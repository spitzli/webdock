# Native Control Plane

The Rust service boots with Loco, accesses PostgreSQL through SeaORM and exposes native account, OAuth/OIDC, registry and hosting HTTP paths and a same-origin browser facade. This is an in-progress migration, not full platform parity. The complete ledger is `docs/verification/2026-10-19-rust-platform.md`.

For local development, run `tilt up` from the repository root (Docker, the pinned Rust toolchain and Bun required). It starts a loopback PostgreSQL, generates private credentials in `.dev-local/`, provisions the restricted roles, applies migrations, bootstraps a local operator once (credentials are printed in the `database` resource log), then serves Core on 3130, the Console on 3121 and the account surface on `localhost:3125`. Set `WEBDOCK_DEV_FEATURES` to a feature JSON object to enable optional modules. Tilt also runs a loopback OCI registry (`127.0.0.1:5005`) and seeds a Demo customer/project with the `plugins/echo-demo` extension: its image is built and pushed to that registry, and the release, installation, runtime, configuration and project grant are recorded directly, as a reviewed installer would. `plugin-control`, `plugin-controller` and the plugin itself run as local processes on private Unix sockets. The separately configured [native initial plugin installer](../../docs/operations/native-plugin-installation.md) is now implemented as an opt-in path. Tilt's direct Echo seeding exercises availability, grants, discovery and invocation (the project page shows the Echo demo panel); it is not fresh-install acceptance. `docker compose -f deploy/dev/compose.yaml down -v` resets the database. For passkeys with password managers that refuse plain-HTTP `localhost` (for example 1Password), run `WEBDOCK_DEV_HTTPS=1 tilt up`: Console and account pages are served over HTTPS with certificates from a locally trusted CA (install `mkcert` and run `mkcert -install` once). Origins are recorded at bootstrap, so switching between HTTP and HTTPS needs a database reset.

Otherwise, configure variables from `.env.example` in the process environment, then run `cargo run -p webdock-control-plane`. The service does not implicitly load production environment files. It verifies the exact restricted authentication and registry roles and rejects owner/BYPASSRLS privileges. Production database connections require verified TLS. Existing host-only auth cookies, signed transaction-local RLS context and immutable local IDs remain in use; no external identity service is called.

`WEBDOCK_DATABASE_URL` is the authentication-only `webdock_auth_bootstrap` connection. `WEBDOCK_REGISTRY_DATABASE_URL` is the independently restricted `webdock_registry_runtime` connection. The allocator opens a separate small authentication-role pool to reserve IDs before returning them, including while a caller holds a business transaction.

The React development server uses Console port 3121 and a second instance on canonical auth `http://localhost:3125`; both proxy their registered API paths to port 3130 while preserving Host. API/Console/Studio can retain `127.0.0.1`; WebAuthn requires the auth RP domain `localhost`, not an IP address. Browser-facing configuration selects the account surface or same-origin Console facade by exact host. The first-party confidential Portal client performs authorization code + PKCE and ID-token verification server-side; browser cookies contain only signed opaque identifiers. Password/MFA/passkey/security UI runs on the canonical auth origin. No credentials are put into JavaScript storage. Existing protocol hostnames and `/api/sso/*` paths remain explicit host routes; RP/origin restrictions are never relaxed.

## Offline migrations

The runtime performs no schema convergence, truncation, seeding or queue-table creation. Apply the reviewed native migrations explicitly:

```sh
cargo run -p webdock-control-plane --bin webdock-migrate -- --target localhost:5432/webdock
```

Supply `WEBDOCK_MIGRATION_DATABASE_URL` only to that offline process. The supplied target must match its exact hostname, port and database. Retained migration IDs/checksums must match the release baseline. Native migrations then run with SQLx's checksum/journal/locking engine on the existing SeaORM pool; historical migrations are never silently reinterpreted. Ordinary runtime roles are rejected.

For a new empty database, `--initialize-empty` installs the bundled schema baseline and the supplied `DATABASE_RLS_SECRET`. Restricted login roles and NOLOGIN ownership roles must already be provisioned, or explicitly provide `--provision-roles-from /absolute/private/roles.json` together with `--initialize-empty` using a PostgreSQL administrator connection. The private JSON maps the eight fixed runtime role names listed in `webdock_persistence::roles::LOGIN_ROLES` to independent base64url/hex secrets (32–256 characters). The provisioner creates only missing roles and refuses unexpected privileges/membership. It never changes existing role passwords or privileges. Any existing user relations/platform schema cause refusal. The baseline contains structure/policies only, no customer records or signing key. The same native migrations finish initialization. Real PostgreSQL tests cover initialization, refusal to reinitialize, exact retained history and restricted-role denial.

Database URLs must identify the user, host and database directly. Query parameters cannot override credentials or the target, and duplicate TLS-mode aliases are rejected. Non-loopback connections require an explicit `sslmode=verify-full` (or the driver's `ssl-mode` alias); production also requires it for loopback. A missing port becomes explicit 5432, and development loopback without a TLS mode becomes explicit `prefer`, so `PGPORT`/`PGSSLMODE` cannot silently change those choices. Unknown query keys are rejected before the driver can log their values.

`webdock-bootstrap-operator --target localhost:5432/webdock --config /absolute/private/operator.json --output /absolute/private/initial-secrets.json` performs the native first-install operator transaction. Include the optional ninth `webdock_offline_migrate` password in the explicitly reviewed fresh-role map; the bootstrap never uses a runtime login or a database superuser. Set `DATABASE_URL_UNPOOLED` to that dedicated login and provide the same `WEBDOCK_AUTH_SECRET` used by Core. Remote PostgreSQL requires verified TLS and an explicit `DATABASE_CA_CERT` PEM bundle. The exact reviewed host:port/database, original authenticated login, current/session roles, baseline provenance and complete retained/native journals are checked before provisioning.

The private JSON contains `email`, `name`, `password`, `authOrigin`, `studioOrigin` and `consoleOrigin`. Origins must be distinct exact canonical origins and match `WEBDOCK_AUTH_ORIGIN` (or retained `BETTER_AUTH_URL`), `WEBDOCK_STUDIO_ORIGIN` and `WEBDOCK_CONSOLE_ORIGIN`; when both Auth variables are present they must agree. Password may instead come from `WEBDOCK_INITIAL_OPERATOR_PASSWORD`, but never both sources. HTTPS is required except explicit loopback HTTP origins with a loopback database. Input must be an owned private regular file no larger than 16 KiB.

The migration advisory lock and table locks fence concurrent setup. The transaction creates the local operator/account, immutable-subject Registry projection, reviewed Portal client/binding, platform defaults, bootstrap audit records and initial encrypted RSA signing key. Every new ID comes from the committed native allocator. Existing operators, matching emails, clients, bindings, signing keys or bootstrap markers require reviewed administration; no email linking or replacement occurs. Both the native Console and retained Studio callback/logout URLs are registered from the reviewed input. Password replacement and real MFA remain mandatory; bootstrap creates no session, MFA material, notification or provider installation.

The output is exclusively created mode-0600 and is never overwritten. Its complete secrets are flushed, along with the containing directory, before COMMIT. Precommit failure removes the newly created output; an uncertain COMMIT retains it with `status:"verify-command-result"`. Never retry an uncertain result blindly: inspect the recorded operator/client IDs and audit state first. Standard output contains only a nonsecret creation summary. Normal Core startup never mints initial signing keys or runs this transaction.

The owned Docker regression exercises actual CLI refusal/concurrency/rollback, output collisions, password replacement/TOTP followed by Registry writes, PKCE browser handoff on Console and Studio, and a dropped actual PostgreSQL COMMIT acknowledgement with durable output retention. Run with `WEBDOCK_BOOTSTRAP_DOCKER_TEST=1 cargo test -p webdock-control-plane --test bootstrap -- --ignored`. It creates its own PostgreSQL container, eight runtime roles and dedicated migrator, and removes that container and volumes afterward; shared database roles are untouched.

## Current verification boundary

Native HTTP tests complete password setup, TOTP enrollment, registry writes/audit and logout through the real retained-schema database. The React UI has also read real project data from this Rust API. Full product routes, compatibility SSO, plugin-host/controller integration and release cutover remain work in progress. `healthz` liveness is separate from `readyz`, which verifies the restricted role and the exact compiled native migration versions/checksums.

The optional `webdock-agent-control` executable serves the Core-owned agent RPC contract over a private Unix socket or explicitly configured mutual TLS. It uses the same hosting services, independently verified enrollment and durable dispatch records; see `crates/agent-control/README.md`. No Kubernetes or Docker engine credential is loaded into this Core listener.

Fresh-install verification also creates an independently owned PostgreSQL 18 Docker fixture, provisions restricted roles, preserves their credentials on a second provisioning pass, refuses unexpected privileges, installs the complete baseline/native migrations and verifies runtime readiness. The test removes its own container and volumes; existing databases are never reset.


The browser facade is enabled by `WEBDOCK_SSO_CLIENT_ID`, `WEBDOCK_SSO_CLIENT_SECRET`, and `WEBDOCK_SSO_COOKIE_SECRET`; `WEBDOCK_STUDIO_CLIENT_ID` must identify the same retained Portal client when set. Native migration0011 installs authentication-only flow/session storage. Existing Fe26.2 SSO cookies are accepted only when `WEBDOCK_SSO_LEGACY_ACCEPT_UNTIL` explicitly supplies a Unix-seconds deadline no more than eight hours ahead; their original payload/envelope expiration and live client/session authority still apply. No legacy seals are minted. Account security remains on authOrigin, including passkeys; Console delegates only its exact registered first-party client and checks current authority on every request.

Set `WEBDOCK_UI_DIST` to the immutable built React artifact directory to let Core serve Auth/Console/Studio pages through `tower-http` ServeDir/ServeFile. It requires `index.html` at startup. Unknown API, `/v1`, discovery and missing asset paths never fall back to HTML; other hosts cannot receive the UI. HTML is no-store; hashed assets may be cached immutably. Encoded traversal, dotfiles and symlinks escaping the artifact root are rejected. Runtime containers should mount these first-party artifacts read-only.

UI CSP allows self-hosted scripts, styles and API requests. Declare isolated custom-plugin frame origins with `WEBDOCK_UI_FRAME_ORIGINS` and database gateway origins with `WEBDOCK_UI_CONNECT_ORIGINS` (JSON arrays of exact HTTPS origins; explicit loopback HTTP is development-only). These CSP declarations do not grant plugin/API permissions or configure gateway CORS. Core pages cannot be embedded. Dynamic plugin installations must also update the deployment's declared frame allowlist; there is no implicit wildcard approval.

## Native Mail services

With the Mail feature enabled, `WEBDOCK_NATIVE_MAIL_SENDING_ENABLED=true` mounts the native sending-key and queue adapters. `MAIL_SEND_WORKER_SECRET` is a separate confidential credential, distinct from `MAIL_GATEWAY_SECRET`. Sending and queued-Webmail control commands require the worker credential; the browser gateway cannot use its own credential for those commands.

Complete native provider dispatch additionally requires `WEBDOCK_NATIVE_PLUGIN_CONFIG` with a `mail` object containing `signingKey` (an absolute path to an owned private Ed25519 key file), `workerId` and positive `workerGeneration`. The HTTP process and independently supervised `webdock-plugin-control --config /absolute/private.json` must share those issuer/worker settings. The latter mounts MailAuthority beside the existing host/repository services on its private Unix socket or mutually authenticated TLS listener. Both use the same production initializer. Current tenant/provider installation, generation, peer, reviewed manifest, binding and configuration authority are checked inside the domain transaction; message data cannot select credentials or endpoints.

Incoming SMTP dispatch additionally requires `WEBDOCK_NATIVE_MAILBOXES_ENABLED=true`, `MAIL_MANAGED_CLUSTER_ID`, `MAIL_HOSTNAME_SUFFIX` and the retained `MAIL_ENCRYPTION_KEY`. Enabling outgoing sending alone does not activate or provision an incoming engine. Read `crates/mail/README.md` for the independent API/worker process configurations, retained-queue cutover requirements and current verification limits. Provider installation/adoption and full Mail administration remain unfinished migration work.

`WEBDOCK_NATIVE_MAIL_ENABLED=true` separately enables incoming administration with `MAIL_MANAGED_CLUSTER_ID`. It can run without the Webmail gateway or outgoing worker. The existing `/api/console/mail` and `/v1/mail` browser adapter accepts typed `getTenantMailService`, `manageTenantMailService`, `getTenantMailboxes` and `manageTenantMailboxes` commands with `customerID` and, for mutations, `input`. Service changes require the expected string revision. Reads do not allocate an engine; activation queues an explicit authorized request, suspension preserves data, and directory readiness requires observed runtime/configuration state. The Rust incoming executor and its real engine acceptance remain separate unfinished work. This is not permission to deploy or adopt a live instance.

The separately supervised `webdock-agent-control` listener mounts incoming execution only with `WEBDOCK_NATIVE_MAIL_AGENT_ENABLED=true`, enabled native Mail administration and a Mail feature state permitting accepted work. It requires the retained configuration names `MAIL_STALWART_IMAGE`, `MAIL_HOSTNAME_SUFFIX` and `MAIL_ENCRYPTION_KEY`. Use the reviewed immutable digest built from `infra/mail/Dockerfile`: the restricted non-root profile removes the upstream binary's file capability and selects the retained `/data/config.json` path. The unmodified upstream image does not satisfy that execution profile. Image/material validation remains in the typed domain. HTTP admission and the private listener share the same incoming initializer and restricted pools; Core never loads an Engine socket or kubeconfig. Agent enrollment and an explicitly configured, verified runtime remain necessary. This configuration wiring alone is not runtime acceptance.

Domain, mailbox and access configuration execution has its own opt-in: `WEBDOCK_NATIVE_MAIL_CONFIGURATION_ENABLED=true`. The private listener rejects that request unless native Mail administration, agent execution and mailboxes are all explicitly enabled and the Mail feature permits accepted work. An absent flag or `false` leaves configuration execution disabled; other values fail startup without echoing their contents. The enrolled daemon separately enables `mailConfigurationEnabled` in its private JSON configuration and must report the reviewed configuration capability. Lifecycle activation does not imply permission to configure mailboxes or send messages.

Hosting runtime results are available at `GET /api/console/hosting/reads/{operationID}` and `/v1/hosting/reads/{operationID}` after an `apps.logs`, `apps.inspect` or `apps.metrics` request. The typed response exposes status, a sanitized observation when successful and a generic failure message. It never exposes execution envelopes or receipt proofs. Polls require a current authorized browser session, enabled Hosting and live target access; tenant preview cannot access runtime reads.
