# Durable command coordination

`RuntimeSpec` describes a provider-neutral, digest-pinned workload with explicit ownership, resource limits, replicas, container arguments, optional HTTP health probe and retained `/data` volume. Unknown JSON fields, unpinned images, privileged host paths and invalid limits are rejected. There is no host command or arbitrary Kubernetes YAML field.

`Executor` coordinates `Command` execution through a `RuntimeAdapter` and `Authorizer`. Authorization denies by default. A production authorizer must verify enrolled target identity, the persisted Core operation, current resource/project ownership, exact fencing generation and live lease. `LeaseGuard::check_for` prevents borrowing one command's authority for a different operation or specification. Adapters check that binding and recheck live authority before mutating requests. The executor also checks every 250 ms and before acknowledging results. Work ends at lease expiry/revocation or a 300-second execution deadline.

The local `Journal` uses a private directory, no-follow file opens, an exclusive process lock (`fs2`) and atomic file replacement (`tempfile`). Accepted commands are fsynced before runtime I/O; successful observations are fsynced before returning success. The directory is fsynced after replacement. If persistence becomes uncertain, the open journal fails closed until it is reopened. Receipt fingerprints include generation, action, the complete workload specification and a present expected-runtime-ID precondition; they deliberately exclude renewed credentials and lease expiry. A stable payload fingerprint permits a higher lease generation for the same operation only when action/spec/precondition remain identical. Resource fences compare (resource revision, operation lease generation), preserving the distinction between new desired revisions and retries of one operation. Older journal entries without renewal metadata fail conservatively rather than guessing. Completed retries of the same generation replay the exact recorded observation. A higher generation with an identical completed payload enters durable `needs_verification`: under a fresh lease, the executor requests command-aware read-only inspection of actual owned state and verifies its runtime ID, resource revision, desired outcome, storage profile and observation timestamp. It never reapplies the old completed mutation or changes the timestamp on old evidence. An inspection failure remains verification-only across retries and restarts. The new observation is committed before the higher-generation receipt is delivered. Older native binaries do not understand this pending journal state and fail closed; rollback while verification is pending needs an explicit compatible executor version. Reusing an operation ID with changed input or using a stale/competing generation fails.

Interrupted and failed commands remain pending reconciliation. The Core must reissue their authorized command after reconnect; the adapter inspects actual resources before continuing. The journal is a local execution receipt store, not the platform's desired-state database or job queue. It retains receipts and is bounded at 10,000 commands / 16 MiB; exhaustion fails closed. An audited receipt archival policy and queue retry/backoff belong to the production integration, and must preserve generation fences and deduplication.

One journal directory is required per enrolled executor, on durable local storage, mode 0700, owned by the agent UID, with trusted path ancestors. All processes addressing that executor must share it; do not delete it to clear errors. The journal stores operation hashes, ownership fences and observations, not bearer credentials or configuration secrets. Original desired commands remain in the Core's durable store.

`ObservedState` carries an observation timestamp and explicit conditions. Transport failures return errors rather than empty inventories. Read APIs (`inspect`, `logs`, `metrics`) are internal privileged adapter methods: the future network dispatcher must authorize their user/project scope before calling them. This crate does not expose a public RPC service or grant access merely because a caller is local.
