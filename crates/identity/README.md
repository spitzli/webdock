# Identity compatibility and persistence

This crate is the initial Webdock-owned identity implementation. It accesses the retained PostgreSQL schema through SeaORM and never calls an external identity provider. It does not run migrations at startup.

Implemented:

- Existing NFKC/scrypt credentials, constant-time derived-key comparison, random credential generation.
- Host-only signed session cookies, duplicate-cookie rejection, clear-cookie headers.
- Existing versioned and legacy XChaCha20-Poly1305 encrypted account material using RustCrypto implementations.
- Persisted opaque session lookup, current expiry/ban checks, explicit setup/MFA/preview authorization state and owner-scoped revocation.
- Password sign-in with atomic database rate limiting, bounded password verification concurrency and locked credential revalidation. An MFA account receives only a five-minute signed challenge cookie backed by a token digest and credential fingerprint. Email-verified accounts needing initial security setup receive a restricted session; `can_access()` remains false.
- Real TOTP enrollment/confirmation with `totp-rs` 6, preserving raw UTF-8 legacy secrets, SHA-1/six digits/30 seconds/one-step skew. Enrollment rotates sessions only after verified proof.
- Single-use persisted MFA challenges, five attempts per challenge, ten failures per account with fifteen-minute lockout, transactional TOTP step replay prevention and recovery-code consumption.
- Password replacement, session listing and revocation of other sessions/challenges. Security mutations recheck account/session/credential state under locks.
- Offline/invitation account insertion and serialized first-operator bootstrap, with real password/MFA setup required. Offline bootstrap asserts installation ownership; it is not an email verification delivery flow.
- Account activation/password reset bound to the existing local ID, email and credential fingerprint. One-use hashed tokens expire after an hour; completion revokes sessions/challenges and preserves MFA.
- Encrypted durable recovery delivery jobs with leases, bounded retries and an injected `Delivery` sink. The default sink reports unavailable and never sends email; sinks must deduplicate on the stable job ID.
- Passkey registration and discoverable sign-in through `webauthn-rs`, using five-minute one-use server-side ceremony state, required user verification and existing RP/origin settings. Existing standard-base64 COSE credentials are imported using the library's parser; no private keys or custom signature algorithms are introduced. Counter/replay checks, owner-scoped rename/deletion and password recovery fallback are enforced.
- Fifteen-minute/eight-hour session renewal, owner-scoped revoke-one by ID or legacy token, MFA disable with session rotation and recovery-code regeneration.
- HMAC-signed, transaction-local database scopes compatible with retained RLS policy functions. The SQL policy remains responsible for rechecking current authorization on business queries.

`IdentityService` must use the restricted authentication pool (`AUTH_DATABASE_URL`, database role `webdock_auth_bootstrap`), not the business role `webdock_auth_runtime`. The four additive SQL migrations must be applied offline before startup. The passkey migration intentionally rejects duplicate existing credential IDs instead of guessing their ownership. `0002_authentication_preview.sql` supplies a policy-owner boolean helper so authentication can detect its exact session preview without receiving direct preview-table read permission. Business operations use a separate restricted pool and `RlsSigner::begin` or `apply` on the same SeaORM transaction as their queries. Callers must require `Principal::can_access()` for business access and `is_operator()` for operator work. Existing cookies can resolve a setup-only principal so account setup can be displayed. A preview row, including an expired one, suppresses operator authority; tenant preview permissions are resolved by SQL policy, never inferred from the principal.

The HTTP layer owns canonical host/origin/CSRF checks and per-IP/global request limits. The service's persistent per-account password throttle does not replace those controls. Neither session tokens nor `IssuedSession.set_cookie` belong in JSON or logs. `create_local_account` is an offline/authorized invitation primitive, not public registration. `revoke_session` must receive the authenticated owner's ID.

Retained external identity mapping rows are migration evidence. These accounts fail closed until a separately audited activation/cutover retires their mappings. This crate deliberately does not trust stored external role projections or link identities by email.

The security setup flow is: offline `provision_first_operator` → `authenticate_password` setup session → `change_password` → `begin_totp_enrollment` → scan the returned URI and securely retain the recovery codes → `confirm_totp_enrollment`. Subsequent password sign-in returns `MfaRequired.set_cookie`; only `complete_mfa` accepts it. Append `clear_mfa_cookie()` alongside the new session cookie on successful completion. Never accept the returned bare user ID as authentication proof. Configure the retained encryption key ring through `with_secret_keys`.

Account recovery requires `with_account_origin` and the retained encryption keys. `request_password_reset` deliberately returns the same empty success for unknown accounts; the HTTP layer must preserve that generic acknowledgement. `queue_account_activation` is an operator/invitation-service primitive for an existing canonical local ID, not public registration. `complete_password_reset` consumes the mailed token and never disables MFA. The HTTP service records encrypted recovery jobs; the separate `webdock-account-delivery` executable in `crates/mail` drains both this outbox and Access invitations through the native HTTPS Mail API. The sink uses `account:<job-id>` idempotency and strict durable queue receipts; lost acknowledgements and dispatcher restarts do not create another Mail job. `delivered_at` records transfer of responsibility to the Mail queue, not inbox delivery. The same shared account-origin validator accepts HTTPS and explicit loopback HTTP development origins; Mail API credentials always travel over HTTPS. For development, Core drains both outboxes itself to a loopback SMTP catch-all when `WEBDOCK_ACCOUNT_SMTP` is set. `queue_account_activation` returns the one-use link and may name the invitation the activation continues into; `complete_password_reset` returns the account email so that page can sign in next.

Passkeys require `with_passkeys(auth_origin)`. `PasskeyChallenge` contains browser options and a Set-Cookie header; ceremony state is stored only in PostgreSQL, despite the library feature permitting serialization. Clear the challenge cookie on completion. Existing random WebAuthn user handles are supported by credential-ID lookup; no UUID/email-based account linking occurs. Newly issued opaque WebAuthn UUID handles do not replace canonical account IDs. The verifier uses the platform OpenSSL library, which must be available in packaged runtime images.

Not yet ported: organization membership invitation acceptance/administration, separate email-change verification, remembered-device MFA bypass, OAuth/OIDC/consent/MCP issuance and external-to-local activation tooling. Native delivery and hardware/browser passkey acceptance still need integration. The identity runtime is not yet at full account/protocol parity.

## Verification

`cargo test -p webdock-identity` tests synthetic Node-generated password, cookie and encryption known-answer fixtures. The generation source is `tests/generate-vectors.mjs`; its output contains synthetic fixtures only.

`WEBDOCK_IDENTITY_TEST_DATABASE_URL=... cargo test -p webdock-identity --test persistence -- --ignored` exercises a real disposable PostgreSQL database whose name ends in `_test`. `tests/fixture.sql` creates test-owned retained-schema subsets, replaces its fixture allocator and resets fixture data; use an isolated identity test database, not another test suite's database. It is not a platform migration. `--test security_flow -- --ignored` uses the same isolated database to exercise the full operator setup/MFA/recovery path, concurrent challenge completion, replay/expiry/credential-change rejection and lockout.

`--test restricted_security -- --ignored` instead requires the explicit retained-schema fixture configuration (`AUTH_DATABASE_URL`, `DATABASE_URL`, `WEBDOCK_TEST_MIGRATION_DATABASE_URL`, `DATABASE_RLS_SECRET`, `BETTER_AUTH_SECRET`). Its strict preconnection guard permits only the local `webdock_rls_test` fixture. It applies only the additive identity migrations and creates/removes its own unique test account. It verifies real restricted authentication roles, preview helper permissions, denied unscoped secret reads and current-ban enforcement in signed business transactions. It never loads `fixture.sql` or resets the retained database.

The offline platform policy inventory must classify `identity_mfa_challenge`, `identity_mfa_enrollment`, `identity_totp_replay`, `identity_recovery_token`, `identity_delivery_job` and `identity_passkey_ceremony` as authentication-only and preserve the preview helper grant when policies are rebuilt.

The new runtime must call `with_allocator(Arc<IdAllocator>)` backed by a dedicated pool. Every new user/account/session/factor/rate-limit/passkey/delivery ID is then explicitly allocated through the durable Rust allocator; existing IDs stay unchanged. Missing allocator configuration retains the legacy database allocator only for transitional tests/callers. The restricted-role integration test verifies allocated identity slots across these tables.

Additional isolated tests: `recovery_flow` exercises captured activation/reset delivery, expiry/reuse denial, session revocation and renewal. `passkeys` uses the maintained software authenticator to produce real cryptographic signatures, checking COSE storage/import, origin/UV/counter/replay/expiry denial and owner deletion. The test authenticator lacks resident storage, so only its local client selection is overridden; production browser options remain resident-required. These are not claims of physical authenticator or browser testing.
