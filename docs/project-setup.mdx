## Anwendung hinzufügen

Öffne dein Projekt und wähle **Anwendung hinzufügen**. Der Assistent speichert deinen Entwurf im Projekt. Du kannst ihn später fortsetzen. Ein gespeicherter Entwurf startet noch keinen Container und bestellt keine Datenbank.

1. **Quelle:** Verbinde ein autorisiertes GitHub-Repository, gib ein unterstütztes unveränderliches Container-Image mit `@sha256:` an oder starte mit der HTTP-Prüfdienst-Vorlage.
2. **Anwendung:** Lege Name, HTTP-Port, Ressourcen, Healthcheck und Umgebungsvariablen fest. Werte von Umgebungsvariablen werden nach erfolgreichem Speichern ausgeblendet; ihre Namen bleiben sichtbar.
3. **Dienste:** Verbinde eine vorhandene PostgreSQL-Datenbank oder wähle einen angebotenen Datenbanktarif. Optional kannst du einen eingerichteten Mailversand mit verifizierter Absenderdomain verbinden.
4. **Prüfung:** Prüfe Quelle, Ressourcen und Dienste. Akzeptiere jedes neue Datenbankangebot ausdrücklich, bevor du **Anwendung bereitstellen** wählst.

Die Prüfung zeigt fehlende Berechtigungen, Hosting-Zuteilungen oder technische Voraussetzungen. Ein Projekt braucht zugewiesenes Container-Hosting. Bei fehlender Zuteilung kann ein Operator sie einrichten. Projekte mit bestehendem Vercel-Hosting behalten ihren bisherigen Bereitstellungsweg.

## Git und Container

Jede Anwendung hat eine eigene Repository-Verbindung mit Branch und Stammverzeichnis. Mehrere Anwendungen können unterschiedliche Verzeichnisse desselben Repositories verwenden. Der Build erwartet eine `Dockerfile` im gewählten Verzeichnis. Die Prüfung bindet einen konkreten Commit; die Repository-Analyse führt keine Skripte aus.

Isolierte Builds benötigen eingerichtete Build-Kapazität und Registry-Speicher. Für GitHub Actions muss der angezeigte Workflow samt Artefaktvertrag bereits eingerichtet sein. Webdock installiert ihn nicht automatisch. Ein Release, das eine Freigabe braucht, zeigt einen Link zur passenden Bereitstellung.

Container-Tags und beliebige private Registries werden nicht automatisch importiert. Nutze einen vom Cluster unterstützten unveränderlichen Digest. Die erste Version unterstützt Anwendungen mit HTTP-Healthcheck; reine Hintergrundprozesse brauchen eine separate Laufzeitkonfiguration.

## Datenbank und Mail

Eine PostgreSQL-Verbindung setzt eine bereite Datenbank im selben Projekt und Cluster voraus. Webdock hinterlegt den Anwendungszugang und die CA für eine TLS-verifizierte Verbindung. Standardmäßig heißt die Variable `DATABASE_URL`. Verwalte diesen Wert über die Dienstverbindung.

Für Mail wählst du eine bereite native Mailverbindung und eine verifizierte Domain. Webdock erzeugt einen auf den Versand und diese Domain beschränkten Schlüssel. Standardmäßig erhält die Anwendung `WEBDOCK_MAIL_API_KEY` und `WEBDOCK_MAIL_API_URL`. Die Netzwerkroute zum Mail-API muss freigegeben sein.

**Mailversand aktiviert keine Postfächer.** Eingehende E-Mails, Postfächer und Weiterleitungen aktivierst du gesondert im Mailbereich. Das Abschalten behält Daten; Löschen ist ein eigener Vorgang.

## Kosten und Wiederaufnahme

Vorhandene Dienste behalten ihre Preise und Limits. Neue Datenbankangebote zeigen Preis, Währung, Bedingungen und Backup-Status. Ein abgelaufenes Angebot muss neu geprüft und akzeptiert werden. Zusätzliche Speicher- und Containerressourcen müssen in dein Hosting-Kontingent passen.

Der Fortschritt unterscheidet Vorbereitung, Dienstverbindungen, Build, Release und tatsächlich beobachtete Bereitschaft. Bei einem Fehler bleiben bereits angelegte Ressourcen erhalten. Behebe den angezeigten Grund und wähle **Einrichtung erneut versuchen**. Eine abgelaufene Sitzung erfordert erneute Anmeldung. Unklare Deployment-Zustände müssen gegebenenfalls durch einen Operator abgeglichen werden.

Unter **Dienste** kannst du Verbindungen prüfen, Mail-Schlüssel wechseln und Dienste von Anwendungen trennen. Das Trennen löscht keine Datenbank. Änderungen an laufenden Anwendungen werden erst nach bestätigtem Rollout als verbunden angezeigt. Bereits provisionierte Konfiguration änderst du in der Anwendung und ihren Diensten.
