# Pizza2400 Implementation Plan

> Execution: inline in this session, following the user's “mach mal”. Use executing-plans and focused tests; no further process approval round.

**Goal:** Deliver an independently deployed Pizza2400 demo with editable Payload content, restaurant ordering UX and a Webdock tenant/project/CMS registration.
**Architecture:** Independent sibling repository `pizza2400`; reuse pinned Webdock operator/SSO policy. Commerce types and validation form a small portable module with explicit demo/Stripe/Polar capabilities. Real payment execution stays disabled for this release.
**Tech Stack:** Existing Next.js 16.3.8, React 19.2.8, Payload 4.0.0-canary.37, Postgres, Vercel, plain CSS.
**Spec:** `../specs/2026-10-04-pizza2400-commerce-design.md` (approved 2026-10-04).

## Constraints and review focus
- All orders are simulated; no payment credentials or real restaurant notifications.
- Restaurant site outside Webdock marketing application; scoped database role and host-bound customer sessions.
- Validate money, product availability, quantities and extras server-side; reject tampered requests.
- Endcustomers cannot access CMS, other users' addresses or orders.
- Unknown delivery conditions must be labelled demo conditions; food images are illustrative until approved.
- Duplicate submits reuse one order; deleted/unavailable products produce readable errors.
- Checkout state survives a failed simulation; account and address data never stored in shared public caches.
- Mobile overlays retain keyboard focus and do not hide the checkout action.
- Provisioning reuses identified resources and never alters existing restaurant domains.

## Task 1: Independent application and tested commerce model
- Create `pizza2400/package.json`, Next/Payload configuration, route groups, `.env.example`, `.gitignore`, `README.md` and `design.md`.
- Create `src/commerce/model.ts`, `src/commerce/model.test.ts`: cent pricing, variant/extras validation, bounded quantity, physical-goods provider restrictions and a quote function.
- Test red/green with `node --import tsx --test src/commerce/model.test.ts`; typecheck with `tsc --noEmit`.
- Establish Vercel project linkage and isolated runtime credentials before migration or app startup; keep production credentials out of local tests.

## Task 2: Payload content and secure demo backend
- Create `src/cms/collections.ts`, `src/cms/globals.ts`, `src/lib/cms.ts`, `scripts/seed.ts` and versioned migrations.
- Reuse protected CMS users and SSO. Keep customer records separate; initially expose an explicitly simulated account with synthetic data if verified mail is unavailable.
- Implement `/api/shop/quote` and `/api/shop/order`: validate request shape, re-read CMS catalog, calculate server totals, use unique idempotency keys, persist only demo orders.
- Integration checks: anonymous CMS writes rejected, duplicate submit returns the original order, no real provider calls, invalid quantities and unavailable products rejected.

## Task 3: Restaurant storefront
- Create `src/components/storefront.tsx`, focused dialog/cart/checkout components and `src/app/(site)/styles.css`.
- Build a distinct photographic restaurant homepage, searchable categorized menu, product customization, persistent non-personal cart, delivery/pickup selection and simulated checkout.
- Build a clearly identified demo account with synthetic profile/address/order/payment-method examples; no collection of real cards.
- Render CMS content on the server, including product availability; provide error/loading/empty/success states, reduced-motion and keyboard interactions.
- Verify mobile widths 320/375/414/768 and desktop 1440 via the shared T3 browser, including cart, dialog and checkout.

## Task 4: Tenant, hosting and final verification
- Create reproducible scoped provisioning/registration scripts; use existing Webdock registry APIs/policies and protected operator identity.
- Provision dedicated media storage where available; link CMS SSO and real deployed CMS inventory only after successful checks.
- Deploy the demo to `pizza2400.webdock.dev`, preserving the real restaurant site; verify HTTPS, page, API and CMS.
- Run commerce and access checks, TypeScript and production build. Perform a fresh independent review as required by executing-plans, fix material findings, then record deployment details and limitations in README.
