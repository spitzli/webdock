# Core-only admin implementation plan

> **For agentic workers:** Use subagent-driven-development for the independent extraction tasks and verify the composed result locally.

**Goal:** Start a usable admin installation with core and one selected authentication plugin, with optional products absent from startup; preserve runtime plugin UI/API/MCP.
**Architecture:** Existing application and protocol contracts remain, with explicit startup composition and extension contributions. Trusted authentication owns identity; OAuth/MCP protocol capability is explicitly selected rather than implicitly forcing a second browser provider.
**Spec:** docs/architecture/slim-core.md and the owner's approved next-step sequence.
**Tech stack:** TypeScript, Bun/Elysia, Next.js, PostgreSQL, existing plugins.

## Constraints
- No production changes, live account migrations, destructive data cleanup, new billing, or analytics styling.
- Preserve local IDs, membership revalidation, RLS, revocation and scoped project capability checks.
- Reuse existing admin application; do not add a parallel toy admin.
- Distinguish trusted startup extensions from isolated project plugins and avoid claiming provider independence until proven.

## Tasks
- [x] Extract auth protocol selection: one browser provider, explicit OAuth/MCP capability, no unconditional Better Auth construction for Clerk startup; test authentication denial and selected-only loading.
- [x] Finish generic registry collection boundaries: core-owned users/workspaces/projects/audit, CMS schemas/queries/writes provided by optional extension, retained-resource archive protection preserved.
- [x] Wire admin plugin contributions and core-only navigation: no eager product pages/services for basic admin; genuine runtime plugin panel remains usable.
- [x] Refactor startup domain dependencies and product preflight/readiness into selected composition, add a reproducible real local Core-only startup + authenticated admin/plugin smoke test.
- [x] Run focused and full relevant regression suites, build checks, docs validation, independent review, commit the verified result.

## Review focus
Clerk startup without BetterAuth secrets; missing optional product schemas; unknown/disabled routes; retained-resource operations with disabled modules; plugin capability/RLS admission; existing OAuth issuer/audience compatibility.

## Owner steering and verified result

CMS was removed entirely from active composition instead of completing an installable CMS extension. Historical inventory remains read-only for retention guards. Stall already had its own repository/schema/project; its mandatory Webdock SSO was removed and a locally built production artifact was promoted after review and checks. No Webdock production rollout occurred.

Real-process core startup is tested for Better Auth and Clerk against fresh restricted-role PostgreSQL. Clerk startup has no Better Auth secret; login delegation is covered with verified-provider fixtures, not a real external Clerk account. The local process test uses development mode because production database policy intentionally rejects loopback databases without verified TLS. Console behavior has 80 tests; no authenticated end-to-end browser session for the new local Console is claimed.
