# Authenticated S3 registry implementation plan

> **For agentic workers:** Use superpowers:executing-plans. Keep the approved S3/OCI milestone intact.

**Goal:** Qualify an opt-in internal OCI registry using private S3 storage, without migrating any existing registry.

**Architecture:** Use pinned CNCF Distribution 3.1.2 and its existing S3 driver. Keep Webdock's guarded publisher and digest checks. The operator supplies separate registry authentication/TLS and bucket-scoped S3 credentials through existing Kubernetes Secrets; the reviewed chart publishes only a ClusterIP service. This is internal trusted-worker registry infrastructure, not a customer-facing registry authorization product.

**Tech stack:** Existing Distribution image, Helm, private MinIO fixture, Rust build publisher and Python/Bun fixture tooling.

**Spec:** `docs/handovers/2026-10-25-s3-managed-storage.md`, sections 7 and architecture boundaries.

## Constraints and review focus

- No production registry migration or deployment, no build cache, no shared provider root credentials.
- Preserve TLS validation, private registry auth, digest/manifest checks and current publication authority.
- Disable S3 redirects so registry authentication stays on the read path.
- Disable client deletion, automatic upload purging and GC. Referenced release/rollback bytes must remain readable; reference-aware deletion is a separate future authority, not a TTL.
- Keep S3 data keys separate from builder upload and backup keys.
- Test unauthorized access, actual blob/manifest push/pull, restart without local registry storage, backend credential revocation and recovery.
