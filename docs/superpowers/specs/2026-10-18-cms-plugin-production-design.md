# Managed CMS plugin

Production readiness is the target, not a completion claim. Payload remains pinned to canary `4.0.0-canary.37`; real cluster provisioning, exact-hostname certificate issuance and a matched database/media restore still require recorded acceptance before customer rollout.

## Intent and authorization

The owner requires CMS to be a production-ready optional plugin, including automatic provisioning of new independent CMS instances, databases and persistent media. Existing website CMSs must remain usable with the native editor. Keep Core small. Reuse existing hosting; no additional KVM host, new paid service or shared CMS resurrection. The owner requested autonomous implementation and publication; routine implementation decisions do not need another confirmation.

## Architecture decisions (implementer choices)

- Plugin ID `managed-cms`; `cms` is reserved. Store the independently built plugin in `extensions/managed-cms`, with its own manifest, runtime, UI, Docker target and tests. It is never imported by Core. Publish its image separately.
- Add a new template app `apps/cms-instance`, separate from the retired `apps/cms`. Reuse the installed Payload 4.0.0-canary.37, Next and native `@webdock/cms-ui`; do not describe this Payload dependency as stable. One immutable image serves independent instances through runtime configuration.
- Use one CMS per project initially. An instance owns a logical Postgres database (schema `app`), runtime DML credentials, distinct migration credentials, stable unique Payload and bridge secrets, and a retained `/data/media` volume. UID/GID 65532, read-only root, one replica, Recreate strategy. No provider credential reaches plugin code or browser.
- Managed raster files are immutable: replacement uploads a new media item and updates the content reference. The native editor uses `removeToTrash` only for the reviewed managed media collection with Payload trash enabled. Administrator removal changes trash metadata, hides fresh public reads and normal lists, and retains bytes and quota usage until explicit operator purge. Apply additive migration `20261018_201453_managed_media_trash` before serving the new image; it adds media/version trash timestamps and indexes without replacing existing tables or files. A failed/concurrent removal must retain the file and roll back metadata.
- Fixed content model: protected subject-linked users; localized pages with title, slug, structured editable content and SEO; raster media with alt text; site settings/navigation. Locales en/de. Explicit editor module allowlist. No arbitrary schema designer, commerce or shared multi-tenancy.
- The native editor supports collections/globals, nested fields, localization, draft/publish, history/restore, media and optimistic concurrency. Add injectable transport without changing the existing same-origin default. Preserve opaque unsupported values. Do not replace rich text with a destructive string conversion.

## Host contract and provisioning

Core exposes generic approved application templates, not CMS provisioning code. Extend apps service with `provision({template_id,name,request_id})` and `provisioningStatus({provisioning_id})`. Require `plugin.apps.provision` for allocation and `plugin.apps.read` for status. A template is operator-owned and selects immutable image, sizing, database plan, health/migration policy and publication. No plugin-controlled image, command, credential, cluster, host or database plan. Core-only returns capability_unavailable when Hosting is absent.

Provision returns a durable operation immediately. Optional Hosting adapter persists plugin ID/generation/grant revision/project/subject and immutable console identity reference, associates request ID with setup ID, and reuses setup save/preview/confirm and worker recovery. Exact duplicate request returns the same setup; changed request with same ID conflicts. Revalidate actor and plugin/project grant before every background step. Revocation blocks future effects. Status must be scoped to plugin and project and omit secrets/internal environment.

Reuse setup stages and admission/capacity checks. Add reviewed application migration/bootstrap before deployment readiness: migration credentials exist only in the bounded job, never in running app. Bootstrap identity using immutable Core subject, not email, browser-supplied role or shared operator account. Publication is a generic operator-owned HTTPS route with exact-origin ownership and health verification. Each instance owns an exact-hostname cert-manager Certificate, Ingress and TLS Secret with recorded UIDs. An operator-installed HTTP-01 ClusterIssuer handles issuance and renewal; the agent never copies wildcard certificates or private keys. Wildcard DNS still routes concrete instance names to approved ingress addresses. Renewal remains available while the plugin is disabled. Do not mark ready until migrations, database, media and HTTPS are usable. Partial failure retains recorded resources and resumes without duplicate allocation. Disable revokes access and retains database/media. Purge remains a separate explicit action.

## Editor and site authority

Bind the plugin's HTTP alias to an exact Auth website binding ID, project and origin in trusted host configuration. Auth binding IDs are distinct from app/registry IDs. Recheck live website/project/tenant authorization on every request and inject trusted actor/role server-side. Validate bridge token and instance audience in the CMS endpoint. Local projected role/disabled state further restricts central role. Do not forward browser cookies or accept arbitrary role headers. Existing website integrations are opt-in and preserve their content/schema and independent credentials. The included existing website bridge uses PostgreSQL transfer tables across serverless requests, installed by its explicit `cms:migrate` and accessed with runtime DML privileges; it must not use a local filesystem journal. No implicit old shared-CMS registry dependency.

Reader can read; editor can create/edit/publish; admin/operator can delete/restore. All tenant impersonation previews remain denied by the existing plugin policy. Draft preview is a separate authenticated website function. Native Payload REST must not bypass editor restrictions. Existing CAS timestamps/revisions stay mandatory for updates; ambiguous mutations are not retried automatically.

Transport limits must support real CMS documents/media without unbounded buffering. Keep ordinary plugin frame limits; use bounded chunk/transfer protocol where required rather than raising all plugin calls to 10 MiB. Maximum JSON document 1 MiB; media 10 MiB. Reject malformed/overlong/error bodies, incomplete transfers, cross-project transfer reuse, expired transfers and incorrect digests. Mutation occurs once after validated assembly. Any transport design must also fit the 4.5 MB Console deployment body limit.

## Builder-check resolutions

- Persist host-owned instance binding records, unique by plugin/project/template; request IDs cannot allocate a second CMS. Record setup/app/Auth binding IDs, exact origin and encrypted secret references. Registration is a resumable stage; static operator runtime configuration remains the template approval boundary.
- Plugin disable revokes editor/provisioning access but leaves published content and retained allocation serving. Explicit instance suspension stops public serving without deletion; re-enable reconnects the same instance.
- Trusted bridge authentication may create a missing local user projection by immutable subject on first access, using central role as initial ceiling. Never match by email, recreate a disabled projection, or automatically raise an existing local ceiling. Local restrictions can be maintained by an explicit operator tool, not public user CRUD.
- Transfers live in the CMS adapter, not Core. Independent managed instances use the retained single-process `/data/transfers` filesystem journal; the existing serverless website uses its shared PostgreSQL journal. Upload and download handles cover serialized requests and responses, with 16 KiB base64 chunks, maximum 1 MiB JSON and 10 MiB binary media plus 64 KiB multipart overhead. Bind handles to exact instance/project/actor/grant generation, expire after 10 minutes, and cap concurrent/total storage. Record commit outcomes durably. If execution is interrupted without a recorded outcome, report reconciliation required and never execute that transfer again.
- Preserve existing native adapter limits; introduce explicit managed-instance upload options for 10 MiB media with a separate metadata budget. Decode/validate raster dimensions and use generated filenames. SVG/HTML/executable uploads are excluded.
- Backup means a write-fenced matched DB dump and media archive with hashes and image/schema version, copied to an existing separately hosted backup destination. Retain seven daily and four weekly sets initially. Restore into isolated resources and compare hashes. Confirm existing destination capacity during operational preflight; do not silently treat same-host snapshots as disaster recovery.

## Production acceptance and release

Acceptance requires a real fresh instance: provision twice with the same key; migrate with scoped credentials; edit/publish/unpublish; stale-write conflict; reader/editor/admin and revoked-role checks; cross-project denial; native REST bypass denial; raster upload and persistence after pod recreation; immutable replacement and administrator media trash retaining bytes/quota, including failed/concurrent removal; authenticated draft vs public published content; backup and actual restore of both database and media; disable/re-enable retains content; interrupted provisioning resumes; no credentials in plugin configuration, logs or browser.

Run Core boundary tests and existing managed-apps regression tests. Build independent plugin and CMS images with exact digests, publish through existing signed release machinery, install on existing infrastructure, verify anonymous/public artifact access as intended. Public English documentation explains selfhosting prerequisites, installation, provisioning, roles, backups and retention, and explicitly states any remaining readiness limitation. Add real screenshots only if legible. Never label the feature production-ready from unit tests alone.
