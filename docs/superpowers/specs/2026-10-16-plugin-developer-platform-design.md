# Plugin developer platform: SDK, CLI and host services

Status: planning amendment, 2026-10-16. The owner explicitly requested scaffolding tooling and code APIs for DB, Cache and other host interfaces, and asked us to study Tabularis. This is required delivery scope alongside [runtime plugins](2026-10-16-runtime-plugins-design.md), not optional polish after that plan is declared complete. No SDK or CLI described here is implemented yet.

## What the Tabularis study establishes

Inspected source: [Tabularis `4e10fe0e8a69d19a84b74b183682e107dd81357d`](https://github.com/TabularisDB/tabularis/tree/4e10fe0e8a69d19a84b74b183682e107dd81357d). Source inspection is not a claim that its current npm packages or every documented flow were executed.

| Existing Tabularis pattern | Evidence | Webdock adaptation |
| --- | --- | --- |
| Generator with manifest, executable project, tests, CI and optional UI | [`packages/create-plugin`](https://github.com/TabularisDB/tabularis/tree/4e10fe0e8a69d19a84b74b183682e107dd81357d/packages/create-plugin) | A real Webdock CLI creates a working TypeScript plugin with the same end-to-end development loop |
| Public plugin API package separated from the host | [`packages/plugin-api`](https://github.com/TabularisDB/tabularis/tree/4e10fe0e8a69d19a84b74b183682e107dd81357d/packages/plugin-api) | Publishable SDK, typed host service clients and browser entrypoint; no imports from monolith internals |
| `defineSlot` with a different typed context per UI slot | [`src/slots.ts`](https://github.com/TabularisDB/tabularis/blob/4e10fe0e8a69d19a84b74b183682e107dd81357d/packages/plugin-api/src/slots.ts) | Typed Webdock slots with serializable context and isolated iframe surfaces |
| Settings, theme, translations, notifications and dialogs through host hooks | [`usePluginApi.ts`](https://github.com/TabularisDB/tabularis/blob/4e10fe0e8a69d19a84b74b183682e107dd81357d/src/hooks/usePluginApi.ts) | Consistent public settings/theme/locale and a narrowly validated UI bridge |
| Separate executable and versioned JSON-RPC methods, request IDs, cancellation and shutdown | [`rpc.rs`](https://github.com/TabularisDB/tabularis/blob/4e10fe0e8a69d19a84b74b183682e107dd81357d/src-tauri/src/plugins/rpc.rs), [`driver.rs`](https://github.com/TabularisDB/tabularis/blob/4e10fe0e8a69d19a84b74b183682e107dd81357d/src-tauri/src/plugins/driver.rs) | Preserve a documented language-neutral contract over authenticated HTTPS, with typed TypeScript clients, deadlines and cancellation |
| Load/unload after install and explicit enable/disable | [`commands.rs`](https://github.com/TabularisDB/tabularis/blob/4e10fe0e8a69d19a84b74b183682e107dd81357d/src-tauri/src/plugins/commands.rs) | Existing Webdock lifecycle plan plus registered contribution cleanup and server-authoritative admission |
| Capability/metadata discovery and SDK/host sync checks | [`connection_metadata.rs`](https://github.com/TabularisDB/tabularis/blob/4e10fe0e8a69d19a84b74b183682e107dd81357d/src-tauri/src/plugins/connection_metadata.rs), [`check-sync.ts`](https://github.com/TabularisDB/tabularis/blob/4e10fe0e8a69d19a84b74b183682e107dd81357d/packages/plugin-api/scripts/check-sync.ts) | Required/optional service negotiation plus automated schema/type/host parity checks; discovery never expands granted permissions |

Tabularis is primarily a desktop database-client extension system. Its database-driver interface operates user connections; it is not evidence of a general multi-tenant SaaS DB/cache service for arbitrary plugins. Its UI loader executes IIFE code in the host using `new Function` and shared React globals ([source](https://github.com/TabularisDB/tabularis/blob/4e10fe0e8a69d19a84b74b183682e107dd81357d/src/contexts/PluginSlotProvider.tsx)). Webdock adopts the authoring ergonomics while keeping separate plugin origins and containers. Do not copy that execution boundary or desktop filesystem/credential assumptions. Read-only labels, TypeScript types and feature flags are not authorization mechanisms. Some upstream tutorial/version details lag code; pin source and verify actual release artifacts before reusing code, and preserve licenses if code is copied.

## Package boundaries and developer experience

Create two publishable packages, not one package per host service:

- `@webdock/plugin-sdk` in `packages/plugin-sdk`, with `/contracts`, `/server`, `/ui` and `/testing` exports. `/contracts` is runtime-neutral and shared by the host, CLI and plugin. `/server` wraps the authenticated host-service protocol and runtime request handling. `/ui` runs inside the iframe; it imports no server credential code. `/testing` supplies explicit fakes and protocol/conformance helpers, never silent production fallbacks.
- `@webdock/cli` in `packages/plugin-cli`, binary `webdock`, for authoring and operator lifecycle commands. `npx @webdock/cli plugin create my-plugin` is the canonical scaffold command. A separate `npm create` wrapper is unnecessary for the first release.

Keep existing `@webdock/module-sdk` compatible for bundled modules; re-export relevant pure contracts from the public SDK instead of maintaining two independently drifting plugin schemas. Neither published package depends on private application workspaces. Compiled package exports, schema assets and templates must work from `npm pack` in an empty directory. Node 24 is the CLI floor; the first backend template targets the repository's Bun runtime. The wire contract remains usable from other languages; additional language scaffolds are follow-up work.

Authors use `definePlugin`, `defineAction`, `defineJob`, `defineSchema`, `defineMigration` and `defineSlot`. Action/job input and output schemas produce inferred TypeScript types and runtime validation. A generated plugin has a real read/write sample, tests, a minimal UI when selected, and a release workflow. Unimplemented capabilities return `not_supported`; no placeholder readiness, connection or migration success.

## Code API contract

Backend handlers receive an invocation-local `PluginContext`. Identity/scope, deadlines and grants are attached by the verified host request and cannot be selected with `forTenant(id)` or arbitrary headers. There is no process-global current customer. Parallel invocations cannot leak clients or data between contexts.

| API | Required behavior |
| --- | --- |
| `ctx.db` | Typed plugin-owned relational tables, bounded queries, atomic command batches, generated migrations and retained data |
| `ctx.data` | Existing small JSON-document API for settings/simple records; distinct from relational DB, not advertised as equivalent to SQL |
| `ctx.cache` | Scoped `get`, `set`, `delete`, `getOrSet` with TTL and explicit miss behavior; never a durable store or authorization source |
| `ctx.jobs` | Enqueue/cancel only the plugin's declared jobs, with idempotency, delay and current project grant |
| `ctx.events` | Emit/handle declared plugin-local events through a durable outbox and the existing job execution path |
| `ctx.storage` | Scoped object put/get/delete with size/quota checks, backed by an operator-configured object-store adapter |
| `ctx.config`, `ctx.secrets` | Validated immutable invocation config and individually approved server-only secret references |
| `ctx.http` | Requests to named, operator-approved endpoint bindings with method/path/size/time limits and SSRF protection |
| `ctx.log`, `ctx.audit` | Structured correlated logs and namespaced audit events; cannot forge core/operator audit records |
| `ctx.project`, `ctx.actor`, `ctx.capabilities` | Authorized public context and service availability; no implicit core table access |

Capability names extend the original baseline: `project.read`, `plugin.data.read/write`, `plugin.db.read/write`, `plugin.cache.read/write`, `plugin.jobs.enqueue/cancel`, `plugin.events.emit/subscribe`, `plugin.storage.read/write`, `plugin.secrets.read`, `plugin.http.request`, `plugin.audit.emit`. Every request is further bounded by manifest-declared table/job/topic/secret/binding names and installation/project grants. In particular, read actions cannot mutate DB, cache, storage, jobs or events; an authorized maintenance write must be declared as such. Logs do not authorize audit writes.

Declare required and optional services with protocol versions in `x-webdock`. Missing required services block activation; optional services are visibly unavailable and return a typed `capability_unavailable`. The schema, grant intersection and host checks are mandatory even when the TypeScript method exists. No SDK method is a stub that reports success when its adapter is absent.

Use one versioned method catalog and JSON envelopes for host services: request ID, method, arguments, idempotency key where needed; response result or stable error `{ code, message, retryable, requestID }`. Keep the existing HTTPS action/job endpoints and invocation tokens. Generate runtime schemas, declarations and protocol documentation from the same definitions. No need to introduce a second JSON-RPC stack merely because Tabularis uses stdio JSON-RPC.

The SDK propagates `AbortSignal` and the host deadline; action/job invocation budget remains 30 seconds. It does not automatically replay non-idempotent operations. Cancellation is best effort, with fenced commits and status/idempotency checks determining whether a write happened. Initialize/readiness negotiates protocol and required services and validates config before admitting work. Shutdown drains accepted invocations; a cleanup hook cannot erase retained data or claim authority after lease loss.

## Database service and migrations

Provide actual plugin-owned PostgreSQL tables in the existing platform PostgreSQL instance, not access to arbitrary platform tables and not a customer Databases product dependency. Physical tables live in a dedicated `webdock_plugins` schema with host-generated installation/table names. The manifest owns logical names, columns and indexes. The host owns physical names, mandatory customer/project scope columns, constraints and RLS. A plugin never receives a database connection string.

Use a bounded typed query description, compiled to parameterized SQL by the host. Initial operations are `findOne`, `findMany` with typed predicates/order/cursor, `insert`, `update`, `delete`, and an atomic `transaction` of declarative commands. No raw SQL strings, arbitrary joins, stored functions, SQL expressions or caller-controlled identifiers in v1. Update/delete require an explicit bounded predicate. A transaction is one host request containing up to 32 operations and at most 1 MiB; it does not hold a DB transaction across an asynchronous callback executing in the plugin. Mutations require an invocation-bound idempotency key. Initial reads return at most 100 rows per page, 64 KiB per row and 1 MiB per result, with a five-second statement/transaction timeout. Core transport limits must accommodate these named exceptions to the generic small-message limit.

`defineSchema` supports string, integer, boolean, timestamp, JSON and decimal-as-string columns with explicit nullability/default literals, primary key, scoped unique/index definitions and same-plugin foreign keys. Every primary/unique/foreign key includes customer/project scope where needed; inserting the same logical ID in two projects must work without a cross-tenant conflict oracle. Queries carry the host-authenticated plugin/customer/project scope, parameter binding and database RLS. The gateway cannot accept a tenant override inside a query AST. Keep the existing strong signed database-scope mechanism; a user-settable PostgreSQL configuration value alone is insufficient.

`dataProtocolVersion` is 1; `schemaVersion` is a separate positive monotonically increasing integer. Signed manifests carry schema declarations and ordered, checksummed declarative migrations. Initial operations are `createTable`, `addNullableColumn`, `createIndex` and `addForeignKey` against declared existing keys; validate constraints on existing rows. Do not download/execute arbitrary migration JS/SQL. Destructive changes and application data backfills are explicitly unsupported in this first implementation, not silently skipped.

A dedicated plugin migration process has a separate database role that can create/change only plugin-owned objects in `webdock_plugins`, inspect the narrow plugin migration journal and set required RLS/privileges. API, plugin runtime and ordinary controller roles have no DDL/owner permissions. Extend offline role bootstrap explicitly; never give plugin runtime core schema ownership or distribute the offline migration credential. Schema migration uses an installation lock and one transactional DDL/journal commit before candidate activation, after old writers drain. Failure leaves the old schema active. Additive completed migrations remain after executable rollback; rollback is allowed only when the prior release's declared readable schema range and the host's compatibility check both permit it. Historical migration checksums cannot change.

Keep plugin tables, documents and migration history on disable/uninstall. Reinstall binds to the retained installation identity; grants are separately approved again. A schema-change update invalidates the plugin cache namespace. This replaces the earlier draft's fixed `dataVersion: 1`/document-only limit.

## Cache and background work

Cache keys are host-prefixed by installation, customer, project and cache generation; clients supply only bounded logical keys. Values are JSON up to 64 KiB, TTL 1–86400 seconds, and declared quotas bound entries/total bytes. `get` returns hit/miss; `set/delete` report whether storage succeeded. For availability failures, reads become misses and `getOrSet` executes the loader; permission failures throw and must never be treated as cache misses. `getOrSet` requires both read/write cache grants and write intent before running its loader; read actions use `get` plus an uncached DB fallback. It runs the loader in plugin code and does not promise distributed exactly-once execution. In the pilot, write/maintenance work populates or invalidates cache, while `notes.read` cannot mutate it. No locks, rate-limit authority, sessions or durable state may depend on this cache.

Provide a real shared PostgreSQL TTL-cache adapter as the baseline, so multiple replicas work without provisioning another service. Optionally use the existing Bun Redis capability through a separate plugin-cache adapter when the operator configures it; do not reuse `ViewCache`'s hardcoded kinds/60-second TTL or expose unrestricted Redis commands. Memory-only adapters are test helpers. Both real adapters obey the same isolation, expiration, quota and outage tests. A short connection failure cannot turn a foreign tenant's value into a hit.

Extend the runtime plan's job executions with on-demand enqueue and cancellation. Delay is bounded to seven days; payloads to 32 KiB. Derive customer/project/grant and plugin identity from context. Plugins cannot create new schedules at arbitrary frequencies or enqueue other plugins' jobs. Cancellation stops pending work or requests abort for a running lease; it does not retroactively undo committed effects.

Events initially stay within the same plugin and scope. `defineEvent` provides versioned payload schemas; handlers are declared jobs with independently revocable grants. Publishing uses an outbox and at-least-once delivery, with idempotency per event/handler. `ctx.events.emitOp` can be included in the same host transaction as a DB write. Do not implement an unrestricted cross-plugin/core-event bus or cyclic automatic subscriptions in v1.

## Additional services and boundaries

- Config is validated against the signed manifest and refreshed through the lifecycle revision. `ctx.config` excludes secret values. `ctx.secrets.get(name)` resolves only an individually approved named reference for the current scope and never works in a UI bundle; host/SDK diagnostics redact resolved values. Prefer `ctx.http` bindings that attach secrets in the host when the plugin does not need raw bytes.
- `ctx.http.request(binding, request)` selects a preconfigured base origin, allowed methods/path prefixes and optional host-attached credential. Relative paths cannot override the authority. Reuse the registry fetch policy for DNS/redirect/private-network checks, with separate explicit operator private-endpoint policy. Maximum 1 MiB body/response and ten-second deadline; no proxying cloud metadata or arbitrary request headers. Runtime Internet egress remains denied unless separately approved.
- `ctx.storage` uses the existing operator-configured object-storage capability behind a core port, independent of the optional customer Storage product. Start with an S3-compatible adapter and a disposable local test server; existing Vercel storage may be an adapter only if its semantics match. Do not assume inventory/list-usage code implements object I/O. Host-generated prefixes contain installation/customer/project; prevent traversal and cross-prefix enumeration. Limit objects to 10 MiB and enforce per-grant quotas. The host issues short-lived object transfer tickets bound to the invocation, operation and exact key; GET/PUT/DELETE go through authenticated host streaming endpoints with live grant checks rather than granting raw bucket credentials. No browser base64 payload or frame-message upload. Record content hash and idempotency for upload commit. Retain objects on disable/uninstall; deletion is an explicit authorized plugin action.
- Logs carry plugin/version/generation/request/operation and scope correlation, with size/rate limits and secret redaction. `ctx.audit.emit` writes only a plugin-namespaced event with actor identity supplied by the host, distinct from core-generated audit evidence.

## UI slots and hooks

Keep the generic plugin page and add three initial typed slots: `project.overview.panel` with authorized customer/project context, `project.actions` with the same context, and `operator.plugin.settings` with plugin ID plus redacted configuration only. No arbitrary CSS selector, component import path, DOM access or string-rendered executable code. Slots declare ID, order, relative UI entry and required capabilities in the signed manifest. Use deterministic order `(order, pluginID, contributionID)` and unregister customer contributions on drain/disable/update. The host-rendered operator configuration page always remains available to repair disabled plugins using the retained signed schema. The custom settings iframe mounts only when its runtime is ready and able to serve it; a stopped runtime never supplies mandatory repair UI, and no hidden plugin process is started just to show settings.

`defineSlot` selects the correct context type. `/ui` exports `usePluginContext`, typed `usePluginAction`, `usePluginSettings`, `usePluginTheme`, `usePluginTranslation`, `usePluginToast` and `usePluginDialog`. The host transmits validated serializable theme tokens/locale; translations ship with the signed plugin image. Settings writes use only explicitly declared non-secret user-editable fields and the existing config authorization/revision path. Toasts and dialogs use bounded structured data; no React functions or arbitrary HTML cross `postMessage`. A dialog that displays plugin content hosts another isolated frame. Theme/locale/context changes, timeout/teardown and stale generations have defined cleanup behavior.

Frames bundle their own React runtime when using React; they cannot import the host's React instance across origins. SDK ergonomics mirror Tabularis without promising binary compatibility with Tabularis plugins. Browser code can invoke declared backend actions and approved UI operations, never use `ctx.db/cache/secrets` directly or receive host capability tokens. Buttons in the host use declared labels/icons and target an authorized frame/action, with confirmation for manifest-declared destructive actions.

Attachments use a host-owned transfer flow, not bytes inside frame messages. Add `usePluginFiles` with `requestUpload({ action })` and `requestDownload({ action, key })`; the action must declare the matching storage operation and write/read intent in its manifest. The parent verifies the current membership/grant, opens its own file picker/confirmation, streams through authenticated Console/host routes and returns only scoped object metadata or a sanitized result to the frame. No transfer ticket or browser session enters the iframe. The host invokes the declared plugin action with the verified object metadata; uncommitted temporary uploads have a bounded cleanup policy, while committed attachments retain normal uninstall semantics. Storage service request/ingress limits explicitly permit 10 MiB transfers without weakening ordinary action/JSON body limits; action responses and frame messages keep their smaller bounds and must paginate metadata.

## CLI contract

All commands have `--help`, useful exit codes and `--json` for automation. Authoring defaults are local; no command publishes, installs into production or changes a cluster merely because a scaffold was created.

| Command | Deliverable/behavior |
| --- | --- |
| `webdock plugin create <name> --template fullstack\|backend --services db,cache,... --dir <path>` | Runnable source, public SDK dependency, manifest source, schema/migrations, optional UI, tests, Dockerfile, README and release CI; refuse nonempty/unsafe destinations; no automatic dependency scripts or Git commit |
| `webdock plugin dev` | Start or attach to the explicit local development fixture, watch/rebuild the plugin and reconcile its next development image through the real lifecycle; host stays running |
| `webdock plugin validate` | Validate manifest/schema/slots/capabilities, package exports and SDK/core compatibility without provisioning anything |
| `webdock plugin test` | Execute project tests and SDK conformance against an isolated fixture, with fakes explicitly labelled |
| `webdock plugin build` | Typecheck and build runtime/UI/OCI artifact locally, output immutable artifact metadata; never execute plugin code in the host process |
| `webdock plugin pack` | Produce final manifest and matching universal descriptor using the built image digest, checksums and SBOM/provenance references |
| `webdock plugin publish --registry <url> --image-repository <repo>` | Explicitly push image and descriptor asset, then use scoped Tabularium publication; wait for verifiable integrity, refuse changed same-version bytes; `--dry-run` shows exact targets without writes |
| `webdock plugin install\|enable\|disable\|update\|uninstall\|inspect\|logs` | Call the same authenticated operator APIs as Console; require an explicit configured host/profile, preserve CAS/idempotency and display blockers |
| `webdock plugin doctor` | Diagnose runtime/version/config/registry trust, Docker/local cluster/TLS/network prerequisites and host capabilities; redact secrets |
| `webdock plugin migrate --check` | Check the declared migration chain and readable schema compatibility; does not run production DDL from the laptop |
| `webdock auth login --host <url> --token-stdin`, `webdock auth logout` | Save/remove an explicitly issued short-lived plugin-management token in a private named profile; never scrape browser cookies or embed an operator password |

Manifest source is `webdock.plugin.ts` or an equivalent JSON input; action/schema declarations share definitions where possible. Release output is `dist/tabularium.json` plus identical `<id>-universal.json` bytes and a release lock containing all digests. No timestamps/random IDs in canonical manifest serialization. Distinguish reproducible metadata from fully reproducible OCI layers; pin build dependencies and record actual image digests.

Publishing needs an actual descriptor artifact destination as well as Tabularium and OCI. For v1 use a configured release asset on a supported forge; test with a disposable local forge/artifact fixture. The CLI must reject a missing upload destination rather than pretend the registry stores the artifact. Scoped publisher/forge credentials are secret inputs, never command-line values or committed configuration. Executing `publish` is itself a deliberate external action; local conformance must not perform it against public accounts.

The current operator protocol relies on delegated browser cookies; accepting a CLI bearer token is additional implementation work, not an existing assumption. Add an operator-only Console action to mint/revoke an opaque plugin-management token with scopes `plugins:read` and optionally `plugins:manage`, expiry no later than one hour or the issuing verified session's expiry, and a bound local subject/session. Store only a token hash server-side and show the plaintext once to its authenticated issuer. Every CLI request checks token expiry/revocation and current operator/session/preview authority before establishing the existing signed DB session scope. No refresh token, broad platform API key, email mapping or durable impersonated operator is introduced. Read-only tokens cannot mutate installation/grants/configuration. Browser flows retain CSRF/origin checks; any bearer-specific treatment is limited to successfully authenticated plugin CLI requests and must not weaken other operator routes. Profiles are host-bound with file permissions 0600; environment/stdin token use may avoid persistence entirely. Console permission/identity revocation must immediately invalidate CLI access. Expose authenticated plugin inspect/logs with bounded cursor pagination and redacted values so those CLI commands do not need direct cluster access.

Local development uses the same contracts, authorization, state machine and signed fixture registry. Provision a disposable Kubernetes cluster through a local container runtime and the repository's fixture tools, with enforcing network policy and a local TLS Issuer; avoid an unrelated mock host. Reuse a running dev fixture when supplied. Host reload is unnecessary: rebuild/watch only the plugin image/UI and perform a development-version lifecycle transition. Any dev-only digest/trust profile is limited to that explicit isolated fixture and is rejected by production hosts. No public tunnels, globally edited hosts files, mounted Docker socket inside the API, or mutation of the current kube context by default.

## Acceptance and scope

Project Notes must be produced through the CLI in an empty directory using packed SDK/CLI packages, then extended through public APIs only. It demonstrates a relational note table and additive migration, cache hits/invalidation, background job/event, scoped attachment storage and a typed project slot. Separate conformance fixtures exercise named HTTP/secret bindings and denied permissions. Two concurrent customer/project contexts, two replicas, lost responses, revoked grants and reload/update must preserve isolation.

Required completion includes a developer quickstart, code API reference, wire/schema reference, capability matrix, CLI command reference, compatibility policy and working CI example. Contract/type examples must compile and agree with host behavior. Do not stop at a CLI that creates files while DB/Cache methods are stubs.

This expands the earlier pilot scope materially. The prior rough timeline for a minimal external plugin must not be reused as an estimate for the complete developer platform. Extra language generators, raw SQL, destructive migrations/backfills, arbitrary cross-plugin services, a public plugin marketplace and migration of all six built-in products remain separate work.
