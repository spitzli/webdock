<Note>The current source branch is the native Rust platform candidate. Historical alpha images run the retired TypeScript platform. This guide does not establish a published native release or a production cutover.</Note>

Core serves the API, Console and account UI from one native runtime on their configured hosts. It needs external PostgreSQL, verified database TLS, canonical HTTPS origins and private runtime configuration. Managed product workloads use the existing Kubernetes cluster; local Docker is an isolated test backend.

## Build and configure

Build from the matching source revision:

```sh
bun install --frozen-lockfile
bun run quality
bun run test:distribution
docker build -f deploy/docker/Dockerfile --target core -t webdock-core:local .
docker build -f deploy/docker/Dockerfile --target migrate -t webdock-migrate:local .
```

Use the variable names in `crates/control-plane/.env.example`. Supply private restricted-role database credentials, the existing identity/RLS keys and exact Auth, Console and Studio protocol origins through the runtime environment. Never put offline migration credentials into Core. Configure ingress to preserve those canonical hosts and terminate HTTPS.

For an isolated single-host candidate, `deploy/compose/compose.yaml` runs only Core. Supply a reviewed immutable image through `WEBDOCK_CORE_IMAGE` and a private `core.env` beside the Compose file. It binds to loopback port 3130; ingress is independently managed. `deploy/helm/webdock` is the native Kubernetes candidate and requires a digest-pinned image, an existing private runtime Secret and `apiHost` matching the hostname and optional port of `WEBDOCK_API_ORIGIN`. HTTP probes use that authority to pass Core's host boundary. Plugins and execution listeners need their own explicitly configured processes and private transports.

## Offline schema setup

Run `webdock-migrate` separately with `WEBDOCK_MIGRATION_DATABASE_URL` and an exact target:

```sh
cargo run --locked -p webdock-control-plane --bin webdock-migrate -- --target db.example.invalid:5432/webdock
```

For a fresh empty database, the reviewed CLI supports `--initialize-empty` and explicit role provisioning from a private file. Consult `crates/control-plane/README.md`; initialization refuses existing platform state. For a containerized migration, use the separate `deploy/compose/compose.migration.yaml`, a private `migrator.env`, `WEBDOCK_MIGRATE_IMAGE` and `WEBDOCK_MIGRATION_TARGET`. Starting Core never starts this migration service.

Continue with [initial operator setup](/developers/initial-setup). Preserve retained identifiers, signing material, Mail encryption keys and volumes when adopting an existing installation.

## Rollout acceptance

Before rollout, verify backups and restore, retained schema/history, exact ingress routing, authentication, private listener enrollment, enabled products and rollback after new writes. Stop the old writers before transferring ownership. The repository's local checks do not establish these production properties. The retained parity inventory records remaining native Mail, Hosting and distribution acceptance work.
