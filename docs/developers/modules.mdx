---
title: "Configure installed modules"
description: "Select the six installed product modules, assign process ownership and drain retained services safely."
---

Webdock registers six product modules: `mail`, `hosting`, `databases`, `cms`, `storage` and `billing`. Configuration controls product availability. It does not grant tenant membership, buy a plan, create provider accounts or provision infrastructure.

The core identity, customer/project registry, memberships, plans and usage surfaces remain separate from optional products. Disabling Billing does not remove core plan administration. See [self-hosting](/developers/self-hosting) for the container and Helm distribution, and [authentication adapters](/developers/auth-adapters) for browser-provider selection.

## Select modules

Set `WEBDOCK_MODULES` on the API and each worker, with the same configuration across replicas. Console receives the public state from its authenticated API session; there is no independent Console module switch or public build variable.

```json
{
  "configVersion": 1,
  "modules": {
    "mail": { "enabled": true },
    "hosting": { "enabled": true },
    "databases": { "enabled": true },
    "cms": { "enabled": true },
    "storage": { "enabled": true },
    "billing": { "enabled": true }
  }
}
```

An absent variable preserves existing installation behavior. An explicit configuration disables omitted modules. For a fresh core-only installation:

```sh
WEBDOCK_MODULES='{"configVersion":1,"modules":{}}'
```

Empty or malformed JSON, unknown module IDs/properties, mixed `enabled` and `state` fields, and unsupported configuration versions fail validation. Helm accepts the same configuration as a structured `modules` object and serializes it for the runtime. Its strict schema is generated from the runtime manifests.

## Assign route and worker ownership

`WEBDOCK_API_DOMAINS` and `WEBDOCK_WORKER_DOMAINS` select process responsibilities independently of module activation. A module is unavailable in Console when the API does not own its domain. Canonical origin, authentication foundation and domain-dependency checks still apply.

| Module | Primary API domain | Dedicated worker domain |
| --- | --- | --- |
| `mail` | `mail` | `mail` |
| `hosting` | `hosting` | `hosting` |
| `databases` | `databases` | None; gateway and agent execution remain separate |
| `cms` | `cms` | None; website runtimes remain separate |
| `storage` | `portal` | `storage` |
| `billing` | `billing` | `billing` |

These are ownership names, not a complete API-domain configuration: enabled routes may also require Auth, Portal, Registry or integration domains. Workers require an explicit supported domain list and reject disabled modules. A core-only installation starts no worker. Enabling a module never supplies provider credentials or grants an agent additional privileges.

## Choose a lifecycle state

Use either `enabled` or `state` per entry.

| State | Behavior |
| --- | --- |
| `enabled` | Current identity, permissions, entitlements and provider configuration govern access. |
| `draining` | Registered provisioning operations are refused while supported existing management and reconciliation continue. |
| `disabled` | Product routes, navigation and workers are unavailable. Startup checks retained resources and unfinished operations before accepting this state. |

```json
{
  "configVersion": 1,
  "modules": {
    "mail": { "state": "draining" },
    "billing": { "state": "draining" }
  }
}
```

This example disables the other four modules because they are omitted. On an existing installation, include every module whose resources still need management.

Draining Billing blocks new checkouts, offers, product versions, publication and subscription upgrades. Existing cancellations, reconciliation and allowed downgrades retain their existing paths. Mail draining blocks new connections, domains, mailboxes and first incoming activation; resuming a retained suspended instance remains allowed. Hosting, database and storage provisioning use their registered operation guards. These settings take effect through restart or rollout, not a distributed live toggle.

## Disable an existing module safely

<Steps>
  <Step title="Drain all replicas">
    Roll out `draining` everywhere and stop older replicas that still admit provisioning. Keep the responsible workers and agents running for accepted work, delivery and reconciliation.
  </Step>
  <Step title="Resolve retained resources">
    Use existing authorized workflows to finish, hand over or explicitly remove resources. Suspension retains data. Resolve uncertain provider writes, pending jobs and active bindings; a configuration change does not perform cleanup.
  </Step>
  <Step title="Disable and remove worker ownership">
    Set the module to `disabled` and remove its worker assignment. Startup refuses retained resource rows, unfinished operations, missing preflight policies and incomplete database checks. Apply the required migrations before changing state.
  </Step>
  <Step title="Preserve durable state">
    Retain encryption/signing keys, schemas, journals and required storage. Re-enabling does not move resources or change their provider/account bindings. Database migration, backup and deletion are separate workflows.
  </Step>
</Steps>

Preflight is read-only and does not coordinate old enabled replicas. For Mail, retain incoming-instance storage and encryption keys; outgoing-only use does not allocate Stalwart. System authentication email is independent of customer Mail.

## Develop a module

| Location | Responsibility |
| --- | --- |
| `packages/module-sdk` | Manifests, lifecycle configuration, generated schema, public state and navigation contributions |
| `packages/core` | Stable local identity/session and registry contracts/services |
| `packages/platform-db` | Existing platform schema mappings and typed persistence handles |
| `modules/*` | Product behavior and UI, with explicit server dependencies and public DTOs |
| `adapters/<area>/<provider>` | Concrete identity, provider and PostgreSQL transports |
| `integrations/tabularis-web` | Native database UI launch and gateway policy contracts |
| `apps/control-plane` | Authenticated HTTP composition, runtime configuration and service wiring |
| `apps/console`, `apps/auth` | Filesystem routes, authentication transport and frontend composition |
| `agents/kubernetes` | Independently deployed, scoped cluster execution |

Modules do not import applications or discover runtime credentials through ambient configuration. API wrappers supply authorization, persistence, encryption and provider ports. Client entrypoints contain public DTOs and presentation; cookies, database credentials and provider secrets stay server-side. Existing server actions remain authenticated boundaries, and tenant/resource keys reset action results when context changes.

Modules are known at build time; there is no runtime plugin marketplace. Existing compatibility exports, decimal string IDs, OAuth issuer, Studio protocol URLs and MCP audiences remain stable. Better Auth compatibility and explicitly configured Clerk use the same local authorization model; changing browser providers does not migrate identities or entitlements automatically.

## Verify a change

From a configured checkout using [local development](/developers/local-development):

```sh
npm run test:modules
npm run test:unit -w @webdock/api
npm run check -w @webdock/api
npm run check -w @webdock/admin
node --import tsx tools/release/generate-chart-schema.ts --check
python3 tools/release/check-charts.py
```

Workspace names remain compatible: `@webdock/api` runs in `apps/control-plane`, and `@webdock/admin` runs in `apps/console`. Use the owned disposable database fixture and restricted-role suites for permission changes; never run integration tests against customer databases. Existing providers are the current scope. New cloud services, including AWS/GCP additions, are outside this work.

## Provider directory layout

Adapters are grouped by product area and provider: `adapters/auth/clerk`, `adapters/hosting/vercel`, `adapters/hosting/github`, `adapters/mail/turbosmtp`, `adapters/databases/postgres`, `adapters/storage/vercel` and `adapters/billing/polar`. Better Auth remains in `adapters/auth/better-auth`. Kubernetes runtime metadata is in `adapters/hosting/kubernetes`; its Python executor stays in `agents/kubernetes`.

The root workspace pattern is `adapters/*/*`. Area directories do not become packages. Import stable package names such as `@webdock/adapter-hosting-vercel/projects`; the filesystem grouping does not rename npm packages or protocol routes. Product policy belongs in `modules`, shared contracts in `packages`, and provider-specific I/O in these adapter leaves.
